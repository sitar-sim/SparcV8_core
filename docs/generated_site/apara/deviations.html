    APARA: Deviations and Findings¶

    This project's APARA model is its own implementation of the engine, written from the engine's documents and checked against APARA's reference model. Its sources, in order of authority:

    1. The microarchitecture document (APARA Engine: Microarchitecture and Timing, engine_isp/docs/microarch in the APARA repository), for the engine's structure and timing. Its latency table gives the timing model's default latencies. The timing model has been checked against this document, but not yet against the hardware's own (Aa_model) simulation traces.
    2. The ISA document (engine_isp/isa/isa.txt in the APARA repository), for what each instruction does.
    3. The reference model, McodeMachine, with its tools (mcode_align, mcode_assemble, mcode_run). The narrow-float conversion rules (see Instruction Set) are exactly its rules. Its alignment (mcode_align) and assembly (mcode_assemble) steps are one step in this project's assembler, which uses the same file formats, so files move freely between the two sets of tools; the simulators accept mcode_run's options.

    For every program the reference tools handle correctly, the model gives the same results: the assembler writes the same object file, and a run reaches the same final state (PC, registers, DMEM). This was checked on every valid program of the APARA repository, and on this project's own tests (see Writing and Running Programs).

    This page lists where the model deliberately differs from the reference model, and why, followed by the open questions in the sources, which are to be reviewed with APARA's designers. Every test that depends on a deviation has a DEVIATION line in its .vprj, and the tests of the deviations themselves are collected in validation/apara/deviations/.

    Deviations from the reference model¶

    Each row gives what the reference model does, what this model does instead, and why. Most are fixes of defects in the reference model, where it contradicts the ISA document or its own intent.

    The engine in a system (sparc_apara)¶

    From the hardware's Aa sources (cpu/ccu/ccu.aa, dma/control.aa, data_mem/*.aa), which the reference model does not cover:

    # Source This model Why
    26 dma/control.aa uses control-word bit 3 as interrupt enable, as the error flag on completion, and (written) to clear the interrupt; a command with it set never starts flags [0] scheduled, [1] started, [2] completed, [3] interrupt enable, [4] error one meaning per bit
    27 CCU.TXT calls command 7 "wait-on-complete"; ccu.aa polls (non-blocking), so its interrupt fires only if a poll finds the thread already stopped without interrupt enable, a poll; with it, the command waits for the stop, then interrupts an interrupt a program can wait for
    28 command 8 (step) executes the instruction in R2 at PC R1 one bundle from IMEM at R1, with local data only; R7 := the next PC debugging use
    29 command 9 returns the RAS's 52-bit internal state R6 := depth, R7 := top
    30 (reset leaves registers to the hardware's reset) reset keeps the registers, clears PC, RAS and ERROR registers set before a run survive a reset

    Which addresses are local also follows the hardware: in a system, only the engine's own DMEM window is local, and every other address goes out to the system. The reference model aliases every address into DMEM, and the standalone apara configuration keeps that behavior.

    The system's physical addresses (see The Engine in a System) follow the AJIT_APARA layout, with the addresses APARA's parameter template gives engine 0 of cluster 0.

    Cross-checking against the reference simulator¶

    validation/apara/run_tests.py --reference --mcode-run <path to mcode_run> also cross-checks the model against the reference simulator. For every test without a DEVIATION line, the model writes its final state (the PC, every register, and every DMEM word that is or was non-zero) as a results file, and the reference simulator, given the same program and inputs, must reach exactly that state. This checks the model and the test's own expectations at the same time.

    Open questions in the sources¶

    Where the sources disagree or are silent, the model makes an explicit choice, listed here. D1 to D7 come from the first review of the sources, the rest from the findings since.

    • D1, opcode numbering from 0x16. The Aa_model's parameters.aa and OperatorClassification.txt disagree. The model uses the assembler's numbering (isa/parameters.aa) and keys its latencies by instruction class, not opcode.
    • D2, memory operations per bundle. The microarch doc says at most two (one per DMEM port); the slot rules, mcode_align and the reference documentation allow four. The model allows four, two ports, same-bank accesses one after another.
    • D3, slot rules. The model enforces the microarch doc's (and the assembler produces them).
    • D4, EXEC's structure. "Holds one bundle until the slowest finishes" versus "internally pipelined, full rate". The model is pipelined, results in order; engine.exec.pipelined = false gives the other.
    • D5, latencies. DIV and FSQRT 10 cycles (verbal), VREDUCE 2 and CMOV 1 (assumed): not in OperatorClassification.txt.
    • D6, the parameter template. Its comments and values disagree on the DMEM and configuration base addresses; the model follows the values (they agree with the AFB demultiplexer's decode).
    • D7, a push into a full RAS. Halts the thread (microarch doc) versus "blocks the engine" (ISA text): the model halts the thread.
    • Same-bank order. The microarch doc serializes same-bank accesses in slot order; the Aa_model does not fix an order. The model uses slot order.
    • Exception code 4, "integer square root of a negative number", is in the hardware's exception table, but isa.txt says there is no integer square root. The model has none (the code is unused).
    • The BTB is shared by the four threads; two threads' branches that alias to one entry evict each other. Modeled as described.
    • REGFILE and WRITEBACK. The microarch doc's channel table shows lock releases going from WRITEBACK to REGFILE, its text (from the Aa_model) has REGFILE reading EXEC's results and forwarding them to the retire daemon. The model follows the text; with two tokens it is the version that sustains one bundle per cycle.

    Findings of the validation suites¶

    The validation suites (validation/apara/, validation/sparc_apara/) also turned up places where the engine's ISA and microarchitecture documents are contradictory, ambiguous, or describe a design property worth a decision: for example, whether $set inserts or replaces, the limits of $pack and $dot, the branch predictor training only on mispredicts, returns being predicted by the BTB alone, the throughput limit of two REGFILE tokens, and the lack of an atomic read-modify-write. They are listed, each with the test that shows it, in docs/compliance/apara_specification_findings.md.
